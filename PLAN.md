# Issue Tracker — план разработки

Учебный проект: упрощённый трекер задач (аналог YouTrack / Linear в миниатюре).
Срок — одна неделя. Цель не «сделать красиво», а потрогать руками основные темы бэкенда:
HTTP-слой, работа с Postgres, транзакции, аутентификация, фильтрация и пагинация.

Когда трекер заработает — задачи по его доработке переезжают из этого файла в сам трекер.

---

## 1. Scope

### Входит в MVP

- Регистрация и вход пользователя
- Проекты (ключ вида `TEST`, название)
- Задачи: заголовок, описание, статус, приоритет, автор, исполнитель, номер вида `TEST-12`
- Список задач с фильтрами (статус, исполнитель) и пагинацией
- Комментарии к задаче
- История изменений задачи (кто, что и когда поменял)
- Фронт: вход, список задач, карточка задачи, создание и редактирование

### Сознательно НЕ входит

Эти пункты отрезаны специально — каждый съедает день и не добавляет новых тем:

- Настраиваемые воркфлоу и кастомные поля
- Роли и права доступа (кроме «залогинен / не залогинен»)
- Теги, метки, вложения файлов
- Уведомления (почта, пуши)
- WebSocket, realtime-обновления
- Полнотекстовый поиск
- Канбан-доска с drag-and-drop
- Redis

> Redis вынесен в «после MVP» намеренно. Если останется время — добавляется
> последним шагом как хранилище сессий или rate limit на логин. Тогда будет
> понятно, какую проблему он решает.

## 2. Стек

**Бэкенд**

| Что | Чем |
| --- | --- |
| Язык | TypeScript, Node 24 |
| HTTP | Fastify |
| База | PostgreSQL 14 (в Docker) |
| Доступ к БД | драйвер `pg`, SQL пишем руками |
| Миграции | `node-pg-migrate` |
| Валидация | `zod` |
| Пароли | `argon2` |
| Сессия | JWT в httpOnly-куке (`@fastify/jwt` + `@fastify/cookie`) |
| Запуск в dev | `tsx watch` |

**Фронтенд:** Vue 3 + Vite + TypeScript, Tailwind, Vue Router, Pinia (если понадобится стор).

## 3. Схема данных

Ниже — описание таблиц. SQL миграций пишется руками, здесь только модель.

### users

| Поле | Тип | Примечание |
| --- | --- | --- |
| id | bigserial | PK |
| email | text | NOT NULL, UNIQUE (хранить в нижнем регистре) |
| password_hash | text | NOT NULL |
| name | text | NOT NULL |
| created_at | timestamptz | NOT NULL, default now() |

### projects

| Поле | Тип | Примечание |
| --- | --- | --- |
| id | bigserial | PK |
| key | text | NOT NULL, UNIQUE — префикс задач, например `TEST` |
| name | text | NOT NULL |
| created_at | timestamptz | NOT NULL, default now() |

### issues

| Поле | Тип | Примечание |
| --- | --- | --- |
| id | bigserial | PK |
| project_id | bigint | FK → projects.id, NOT NULL |
| number | integer | NOT NULL — порядковый номер **внутри проекта** |
| title | text | NOT NULL |
| description | text | может быть пустым |
| status | text | `todo` / `in_progress` / `in_review` / `done` |
| priority | text | `low` / `medium` / `high` / `critical` |
| author_id | bigint | FK → users.id, NOT NULL |
| assignee_id | bigint | FK → users.id, NULL если не назначен |
| created_at | timestamptz | NOT NULL, default now() |
| updated_at | timestamptz | NOT NULL, default now() |

Ограничения и индексы: `UNIQUE (project_id, number)`, индекс на `(project_id, status)`,
индекс на `assignee_id`. Статус и приоритет ограничить через `CHECK` или enum-тип.

### comments

| Поле | Тип | Примечание |
| --- | --- | --- |
| id | bigserial | PK |
| issue_id | bigint | FK → issues.id, ON DELETE CASCADE |
| author_id | bigint | FK → users.id |
| body | text | NOT NULL |
| created_at | timestamptz | NOT NULL, default now() |

Индекс на `(issue_id, created_at)`.

### issue_events

Журнал изменений задачи — одна строка на одно изменённое поле.

| Поле | Тип | Примечание |
| --- | --- | --- |
| id | bigserial | PK |
| issue_id | bigint | FK → issues.id, ON DELETE CASCADE |
| actor_id | bigint | FK → users.id — кто поменял |
| field | text | что поменялось: `status`, `assignee`, `priority`, `title` |
| old_value | text | NULL для события создания |
| new_value | text | |
| created_at | timestamptz | NOT NULL, default now() |

Индекс на `(issue_id, created_at)`.

### Два места, где нужна транзакция

Это ключевые учебные моменты проекта, не пропускать:

1. **Выдача номера задачи.** Номер сквозной внутри проекта (`TEST-1`, `TEST-2`).
   Если два запроса одновременно прочитают «последний номер = 7», оба запишут 8
   и упадут на UNIQUE-ограничении. Нужно получить номер атомарно — через блокировку
   строки проекта или отдельный счётчик. Разобраться, чем `SELECT ... FOR UPDATE`
   отличается от обычного `SELECT`.
2. **Редактирование задачи.** Обновление строки в `issues` и вставка строк в
   `issue_events` должны происходить в одной транзакции, иначе история разъедется
   с реальным состоянием задачи.

## 4. API

Все ответы — JSON. Ошибки — единый формат с полями `error` и `message`.
Эндпоинты ниже `/api`.

### Аутентификация

| Метод | Путь | Что делает |
| --- | --- | --- |
| POST | `/auth/register` | email, password, name → создаёт пользователя, ставит куку |
| POST | `/auth/login` | email, password → ставит куку |
| POST | `/auth/logout` | снимает куку |
| GET | `/auth/me` | текущий пользователь |

### Проекты

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/projects` | список всех проектов |
| POST | `/projects` | key, name |
| GET | `/projects/:key` | один проект |

### Задачи

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/projects/:key/issues` | список; query: `status`, `assigneeId`, `limit`, `offset` |
| POST | `/projects/:key/issues` | title, description, priority, assigneeId |
| GET | `/issues/:id` | карточка задачи |
| PATCH | `/issues/:id` | частичное обновление, пишет события в историю |
| GET | `/issues/:id/events` | история изменений |

Ответ списка задач: `{ items: [...], total: number, limit: number, offset: number }`.
Пагинация через `limit`/`offset` — этого достаточно. Keyset-пагинация — тема на потом.

### Комментарии

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/issues/:id/comments` | список комментариев задачи |
| POST | `/issues/:id/comments` | body |

### Служебное

| Метод | Путь | Что делает |
| --- | --- | --- |
| GET | `/health` | проверка, что сервер жив и база отвечает |

## 5. Структура репозитория

```
testback/
├── docker-compose.yml      # только postgres
├── PLAN.md
├── server/
│   ├── migrations/         # node-pg-migrate
│   └── src/
│       ├── app.ts          # сборка Fastify-инстанса
│       ├── server.ts       # точка входа
│       ├── db.ts           # пул соединений, хелпер для транзакций
│       ├── routes/         # разбор HTTP: параметры, валидация, коды ответов
│       ├── services/       # бизнес-логика, транзакции
│       └── repositories/   # SQL-запросы, больше ничего
└── web/                    # Vue + Vite + Tailwind
```

Правило разделения слоёв: в `repositories` живёт только SQL, в `services` — логика
и транзакции, в `routes` — работа с запросом и ответом. SQL не должен оказаться
в роуте, а объект запроса Fastify не должен уехать в сервис.

## 7. Бэклог в формате историй

Истории — для разговора с куратором и для переноса в трекер, когда он заработает.
Формулировка от лица пользователя, критерий готовности — «работает через интерфейс
или через curl».

**Эпик: Аутентификация**
- Как гость, я могу зарегистрироваться по email и паролю и сразу оказаться залогиненным
- Как пользователь, я могу войти и выйти, и после перезагрузки страницы остаюсь внутри
- Как гость, я получаю 401 при попытке дёрнуть защищённый эндпоинт

**Эпик: Задачи**
- Как пользователь, я могу создать задачу в проекте и получить ей номер вида `TEST-1`
- Как пользователь, я вижу список задач проекта и могу отфильтровать его по статусу
- Как пользователь, я могу отфильтровать список по исполнителю
- Как пользователь, я могу открыть карточку задачи и изменить её статус, приоритет и исполнителя

**Эпик: Обсуждение**
- Как пользователь, я могу оставить комментарий к задаче
- Как пользователь, я вижу историю изменений задачи: кто, что и когда поменял

**Эпик: Фронт**
- Экран входа
- Список задач с фильтрами
- Карточка задачи
- Создание задачи

## 8. Definition of Done

Фича считается готовой, когда:

- Эндпоинт отвечает корректно на валидный запрос
- Эндпоинт отвечает понятной ошибкой с правильным кодом на невалидный запрос
- Неавторизованный запрос отбивается
- Изменения в базе консистентны (транзакции там, где они нужны)
- Код разложен по слоям, SQL не протёк в роут
- Коммит с внятным сообщением

## 9. Что разобрать по ходу

Список тем, которые всплывут, и в которых стоит разобраться не поверхностно:

- Зачем пул соединений и что будет, если открывать соединение на каждый запрос
- Что такое транзакция, что гарантирует `COMMIT` и когда нужен `ROLLBACK`
- `SELECT ... FOR UPDATE` и зачем блокировать строку
- Чем миграции лучше, чем «создать таблицы руками один раз»
- Что такое SQL-инъекция и почему параметризованный запрос её закрывает
- Почему пароль хешируют, а не шифруют
- Сессия в куке против JWT: что где хранится и чем отличается
- Зачем индекс и как посмотреть план запроса через `EXPLAIN`
- `N+1` запрос: как он возникает в списке задач с исполнителями
